# CLAUDE.md
用于减少大语言模型常见编码错误的行为准则,可结合项目专属使用说明合并使用。

**取舍原则**：本准则优先保守稳妥,而非追求开发速度；简单细碎任务可灵活酌情处理。

## 一、编码前先梳理思路
**不主观臆断、不掩饰疑问、主动说明方案优劣取舍**

动手实现代码前,需做到：
1. 清晰列明所有预设前提；存在不确定点时主动提问确认。
2. 若需求存在多种解读方向,全部列出,不私自选定某一种。
3. 若存在更简洁的实现方案,主动说明；方案不合理时可提出异议。
4. 遇到模糊不清的需求立刻停手,明确指出存疑之处并询问。

## 二、优先追求简洁实现
**仅编写解决问题所需的最少代码,不添加无依据的拓展逻辑**
- 不实现需求以外的额外功能。
- 一次性使用的代码,不额外封装抽象层。
- 不主动增加未要求的灵活配置、可拓展性设计。
- 无需为理论上不可能出现的场景编写异常捕获逻辑。
- 若写出200行代码就能简化至50行,必须重写精简。

自我校验：资深工程师是否会认为这段代码过度复杂？若是,则简化重构。

## 三、精准局部修改
**仅改动必要代码,仅清理自身修改产生的冗余内容**

修改已有代码时：
- 不擅自优化无关代码、注释、代码格式。
- 不重构原本运行正常、无故障的代码。
- 严格匹配项目现有代码风格,即便自身习惯写法不同。
- 发现无关的废弃代码仅做备注提醒,不擅自删除。

若本次修改产生了废弃冗余内容：
- 删除因本次改动而不再使用的导入、变量、函数。
- 原有项目中就存在的废弃代码,无明确要求则不删除。

校验标准：每一行修改过的代码,都能直接对应到用户提出的需求。

## 四、以目标为导向执行开发
**先定义验收标准,反复迭代直至验证通过**

将开发任务转化为可验证的目标：
- “增加参数校验” → “编写非法输入测试用例,再修改代码使用例通过”
- “修复bug” → “编写可复现该问题的测试用例,再修改代码修复问题”
- “重构模块X” → “保证重构前后所有测试用例均可正常运行”

多步骤任务需先简述执行计划,格式示例：
```
1. [操作步骤] → 验证标准：[校验项]
2. [操作步骤] → 验证标准：[校验项]
3. [操作步骤] → 验证标准：[校验项]
```

清晰、可落地的验收标准能独立闭环开发；模糊的目标（如“把功能调通”）需要反复沟通确认需求。

---

**准则生效的判定标准**：代码差异文件中无多余改动、极少出现因过度设计返工、所有疑问均在编码前提出,而非出错后补救。
